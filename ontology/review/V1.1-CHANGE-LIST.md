### A. Solution keeps only class-level properties

**On the category properties.** The plan (§3.1) keeps `category_id` required
and lets the migration fill it; ontology#20 asked to make it optional, because
it is "required" at 1.7%. Both miss the point that the concept list changes the
question. Each concept carries its `subcategory_id` and `ipcc_action_types`,
and a subcategory belongs to one category. So once a node has a `concept_id`,
these three values follow from it.

Proposal: keep them on the node, as Hazard keeps `hazard_category` beside
`hazard_id` and UrbanSystem keeps `sector` beside `system_id`. But they are a
derived copy with one writer: the seeder copies them from the concept list when
`concept_id` is set, and extraction never writes them. A node with no
`concept_id` has none of the three. "Required or optional" then goes away: the
values are present exactly when the concept is. Two writers would be the real
risk, for example a judge setting the concept and an extractor setting a
different category on the same node.

### B. Deployment detail on edges

D4 sets the rule: no duplicate data. Cost, status and year have one home, the
Action (or the CapitalProject for a budget line). This removes most of what
plan §6 items 7–9 proposed.

| edge | add | mark |
|---|---|---|
| `IMPLEMENTS` Action → Solution | `scale_quantity`, `scale_unit`, `is_primary`. Not `cost_usd`, `status`, `deployment_year`, `equity_focus`, `target_populations`, `local_label`, `local_text` | CONFIRM (D4) |
| `TARGETS` (Plan / Action / CapitalProject → UrbanSystem) | `condition`, `capacity`, `service_coverage`; remove them from `UrbanSystem` | AGREED (D5) |
| `FACES` Action → Barrier | `severity_score`; remove it from `Barrier` | AGREED (D5) |
| `EXPERIENCES` ExposureUnit → Vulnerability | `exposure_score`, `sensitivity_score`, `adaptive_capacity_score`; remove them from `Vulnerability` | AGREED (D5) |
| `PRESCRIBES` Plan → Solution | see 1 and 2 below | **OPEN** |
| `IMPLEMENTED_IN` Solution → Jurisdiction | see 3 below | **OPEN** |

Open points:

1. **`PRESCRIBES`.** D4 speaks about `IMPLEMENTS`, where the Action's name
   already carries the plan's wording. On `PRESCRIBES` there is no Action, so
   the edge is the only home for what the plan calls the thing. Proposed: keep
   `implementation_stage`, `implementation_timeline` and `is_priority`; add
   `local_label` and `local_text`; add nothing else. This is the same case as
   topic F: a plan's phrase is folded onto a shared concept, and the edge keeps
   the phrase.
2. **`implementation_stage` values.** Add `cancelled` for parity with
   `Action.status`, and a definition per value (ontology#18 §2). We would not
   add a `pilot` value (topic D).
3. **Cited cases (D9).** Anthony: `IMPLEMENTED_IN` gains `deployment_year` and
   the citing plan's `PRESCRIBES` is dropped. Our earlier position: with D10 a
   cited case is an Action in its own city, and `IMPLEMENTED_IN` gains nothing.
   The difficulty with a year on this edge: there is one edge per
   (Solution, Jurisdiction), and a city can deploy a class many times, so the
   edge can hold one year and a second cited deployment becomes a conflict. If
   the year stays on the edge, its meaning has to be fixed (for example the
   earliest year a source states).
4. **`Barrier.affected_stakeholder`** is also context: we would move it to
   `FACES`. `Vulnerability.affected_group` stays on the node.

### C. Who an action is for — **OPEN**

Both sides agree the two properties leave the Solution. Where they go:

| | Anthony (D3, and the 10-05 agenda) | Fengze (10-04 comment on adaptbase-core#321) |
|---|---|---|
| v1.1 | `Action —REDUCES_EXPOSURE→ ExposureUnit`, `ExposureUnit —EXPERIENCES→ Vulnerability`; `equity_focus` derived | `Action.target_populations` (bound to `vulnerable-populations`) and `Action.equity_focus` (bound to `enums.equity_focus`) |

Our reasons in one line each: `REDUCES_EXPOSURE` asserts that exposure went

a vocabulary property; only 5 such edges are live. A vocabulary-bound property
can be lifted to edges later without loss.

### D. Action

| change | mark | live data today |
|---|---|---|
| Widen the definition: a parent Plan is not required. Draft wording below | AGREED in direction (D10, adaptbase-core#231); wording to settle | 2,567 of 12,663 Actions (20%) have no `SPECIFIES` |

| `is_pilot` (boolean, written only when true), instead of a `pilot` status value | **OPEN** (our 10-04 comment) | 219 Actions have "pilot" in the name |

`action_kind` (ontology#18 §3) is **not** proposed for v1.1; see section 4.

Draft definition, following adaptbase-core#231: "A specific activity that an actor has
proposed, committed to or carried out in a particular place and timeframe. Most
Actions are specified by a Plan; a specific activity found in a budget, a
progress report or a project page is still an Action when its Plan is unknown.
An Action is the activity, not the asset it builds and not a budget line (that
is a CapitalProject). Distinct from Solution, which is the reusable class an
Action implements."

A format point for the status definitions: enum values declared on a type or
an edge are plain strings today, and none carries a definition. `enums.json`
does (`id`, `name`, `description` per value). The simplest way is to add an
`action_status` block there and bind `Action.status` and
`PRESCRIBES.implementation_stage` to it, as `financing_status` is bound.
adaptbase-core already prefers `enums.json` over the inline list
(`vocab_map.py`); whether the descriptions reach the prompts has to be checked
at adoption.

Also on Plan: `alternative_names` (AGREED). The rename is larger than "126
rows": 35 Plans carry `aliases` today, against 2 on 09-19. The promotion
function writes that key by design whenever it merges a staged unit into an
existing node, so the count grows with every merge. The rename therefore needs
a forward migration of the promotion function (and `review_staging/transform.py`)
before the rows are renamed.

### E. Dated observations for progress properties — OPEN (shape)

A status is true as of a date. Today `status` is one undated value, promotion
keeps the first one, and a newer value is filed as a conflict.

Proposal (ontology#18 §4): progress-type properties are a series of dated
observations, and the scalar, if kept, is derived (latest `as_of`).

- Properties covered: `Action.status`, `Action.financing_status`,
  `CapitalProject.construction_phase`, `CapitalProject.financing_status`,
  `Plan.plan_status`, `PRESCRIBES.implementation_stage`.
- Shape we lean to: on the node, for example
  `Action.status_observations: array<object{value, as_of, as_of_basis, source_type, claim_ids}>`.
  The other shape is an edge (`Plan —REPORTS_ON→ Action {status, as_of}`),
  which needs progress reports to be Plans, and adds a source/target pair.
- `Plan.plan_status` is a free string and needs an enum first (for example
  `draft | adopted | under_review | superseded | expired`).

Why it should be settled now and not later: the Houston status brief (adaptbase-core#336)
reads two reports of different dates, so it can produce two observations for
the same Action, and the CDP status refresh (worklist
item 7) is the first bulk one. Until the ontology declares where a second
observation goes, each of them is filed as a conflict and the graph shows the
first value promoted, not the latest.

What can wait: the ontology only has to declare the shape. The core work
(appending at promotion, the backfill, a researcher lane that looks for newer
sources) can follow in its own time. Every observation is already kept in an
evidence row, so nothing collected in between is lost.

### H. `instrument_type` gaps — NOT IN THE PLAN

Found in the Houston instruments batch: of the 23 instruments the second pass
proposed to accept, 18 were labelled `other`. In the review list the `other`
labels are: tax abatement 7, public-private partnership 6, ground lease 3,
insurance 1, and a few single cases. The brief also expected plain loans.

Before adding values, one thing has to be decided. The ontology has two
vocabularies on the same axis:

| vocabulary | used on | already has |
|---|---|---|
| `instrument_type` (18 values) | the `FinancialInstrument` node, one specific instrument | `green_bond`, `blended_finance`, `grant`, … |
| `financing_model` (12 values) | the `USES_INSTRUMENT` edge (and `FUNDED_BY` under O3), a kind of financing | `public_private_partnership`, `commercial_loans`, `green_bonds`, `blended_finance`, `grants`, … |

Two of the gaps (public-private partnership, loans) are already values of
`financing_model`. So the question is what each vocabulary is for, not only
which values to add.

A reading that is consistent with adaptbase-core#298:

- A **specific, named instrument** is a `FinancialInstrument` node, typed by
  `instrument_type`. Under this reading `tax_abatement`, `ground_lease`,
  `insurance` and `loan` are missing values and should be added.
- A **kind of financing with nothing named** ("through public-private
  partnerships", "grants") is not a node. It is a `financing_model` value on
  the edge, or `Action.funding_types` (O5). Public-private partnership stays
  where it is.

What that reading costs, so it is a question and not a recommendation:
`FinancialInstrument` is an instance type, and about 100 of the 430 live nodes
are named only by a kind ("Grant", "grants", "loans"). They would have to
become properties, as adaptbase-core#298 proposes for generic funders. adaptbase-core#298 did not cover
instruments. It would also change the Houston count: its six public-private
partnership units would stop being instruments.

The same border runs through topic I. Today a named bond or a dedicated fund
is claimed both as a source and as an instrument: 14 names are staged under
both types.

### I. Financing model, O1–O5 — NOT IN THE PLAN

adaptbase-core#298 asks for five ontology changes. None of the plan files
lists them for v1.1, but "no FinancingSource promotion before O1–O5" is the
standing rule, so leaving them out keeps funders frozen until v1.2.

- O1. Narrow `FinancingSource` to a named funding stream; drop "generic types"
  and `amount_usd` from the node.
- O2. `FUNDED_BY` may target `Stakeholder`; `CHANNELS_THROUGH` may start from
  `Stakeholder`.
- O3. `FUNDED_BY` properties: `amount`, `currency`, `amount_qualifier`,
  `period`, `funding_status`, `financing_model`.
- O4. New edge `ADMINISTERED_BY`: FinancingSource → Stakeholder | Jurisdiction.
- O5. `Action.funding_types[]`, bound to `financing_model`.

O2 and O4 change which types an edge may connect. With them in,
`predicate_edges` changes, and so does what promotion accepts. Without them
(and without the edge shape in topic E) the whole version only adds and removes
declared properties and vocabulary terms.

The five belong together: narrowing `FinancingSource` (O1) without O2 leaves
organisations with nowhere to go.

Decision needed: is adaptbase-core#298 a go, and do O1–O5 ride in v1.1?

## 4. Explicitly not in v1.1

  As a declared property they are not ready: they were drawn from one plan's
  41 actions and used on two cities; 12 of Houston's 81 actions came out
  `unclear`, and that bucket mixes "too little text" (Bayou Greenways 2020),
  "a goal, not an action" and generic CDP labels; they are not aligned with the
  IPCC action types the ontology already binds on Solution; an action can be
  more than one kind; and no agreement between runs or with a human reader has
  been measured. Once Solutions are repaired, much of it can also be derived
  from the Solution an Action implements.
